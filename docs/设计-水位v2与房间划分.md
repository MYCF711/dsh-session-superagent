# 水位 v2 与最小交付房间

> 目标：让「未列条目被吞、ack 后复活、自唤醒、截断丢评论、人工恢复不触发」这一族问题在结构上不可表达，而不是继续增加补丁。
>
> 执行纪律：一个房间一个房间验收；当前房间未通过，不进入下一个。

## 〇、公理

### 公理 0：最小交付房间与可选针脚

每个功能房间独立交付、独立验收，只经公开端口协作，禁止跨房间读写内部状态。
端口采用「少量必需针脚 + 显式可选针脚」；调用方只依赖自己使用的能力，缺失可选能力必须明确提示，不得静默降级。

配套铁律：端口契约先行。新功能先声明针脚与一致性用例，再接实现。

### 公理 1：新鲜度属于条目自己

条目是否新鲜，只由该条自己的 cursor 与交付/处置记录决定。全局水位只允许用于首次同步，不参与后续新鲜度判断。

### 公理 2：每个事件只写自己那一行

observe、deliver、handle 只修改对应 `obs[key]`，不得借一次单条动作推进其他条目的状态。

### 公理 3：时间用于节流，轮次与 cursor 用于状态

客户端时钟和上游 `updated_at` 都可能被自己的写操作推动。交付顺序由单调 `round` 表达；条目内容位置由不透明 cursor 表达。时间戳只用于重试冷却、限额和展示。

## 一、状态模型

每个 watcher 只有一张条目表和一个轮次：

```jsonc
{
  "watermarkVersion": 2,
  "round": 137,
  "obs": {
    "issue:134": {
      "cursor": "h:9f2a…",                 // 该条自己的基线，不是整页水位
      "delivered": { "cursor": "h:9f2a…", "round": 135, "at": "…" },
      "handled":   { "cursor": "h:a811…", "round": 136, "at": "…" },
      "retries": 1,
      "round": 136                         // 行级 LWW 依据
    },
    "pr:131/comment": {
      "cursor": 998877,
      "delivered": { "cursor": 998877, "round": 130, "at": "…" },
      "handled": null,
      "retries": 0,
      "round": 130
    }
  }
}
```

`delivered` / `handled` 同时保存轮次和 cursor 是必须的：ack 自己可能产生标签或评论更新。ack 完成后把**该条**的 `handled.cursor` 对齐到处置后的上游位置，自己的写操作不会再次变成新动态；之后出现真正的外部更新，cursor 再次不同，仍会成为新动态。

cursor 是不透明值：issue 使用语义指纹，PR 评论使用评论 id。比较器由数据源声明，状态房不理解 GitHub/Gitee 的字段。

## 二、三个事件与不变式

```js
observe(key, cursor, round)   // 只建立/对齐该条基线
deliver(key, cursor, round)   // 只在交付成功后写 delivered
handle(key, cursor, round)    // 只在处置成功后写 handled
```

- **I1**：事件只写自己的目标行。
- **I2**：`round` 单调递增；`delivered.round` / `handled.round` 不回退。
- **I3**：handle 不推进任何其他条目的 cursor。
- **I4**：未交付的条目不得因为被观察到而失去 fresh 资格。
- **I5**：合并按行轮次做 LWW；旧快照不能覆盖更新的处置记录。

## 三、派生判断

决策房只读当前条目和 obs 投影：

- `unchanged`：当前 cursor 等于该条基线，且没有未处置交付；
- `fresh`：当前 cursor 不同于该条交付/处置位置，需要进入候选；
- `retry`：当前 cursor 等于已交付 cursor，`handled.round < delivered.round`，且冷却与次数允许；
- `handled`：当前 cursor 等于处置后的 cursor；
- `capped`：仅由预算决定，与时间戳水位无关。

`pending`、`lastReported`、全局新鲜度 cursor 不再作为存储事实；重试是派生结果。

## 四、房间与端口

| 房间 | 拥有 | 公开端口 | 不得做 |
|---|---|---|---|
| 状态房 | `obs`、`round`、行级合并、迁移 | observe / deliver / handle / merge | 不联网、不理解 provider 字段 |
| 决策房 | fresh/retry/限额/批次 | decide(input) | 不写状态、不直接发送 |
| 数据源房 | GitHub/Gitee、issue/PR 适配 | capabilities / list / cursorOf / compare / 可选 comments、ack | 不解释交付状态 |
| 交付房 | 会话唤醒与明确回执 | deliver(batch) | 不提前写 delivered |
| 调度房 | interval、退避、暂停恢复、人工触发、inFlight | shouldRun / run | 不判断条目新鲜度 |
| 投影房 | 面板、工具、诊断的只读视图 | projectWatcher | 不回写状态 |

依赖方向：调度 → 数据源/决策 → 交付 → 状态 → 投影。禁止回边；由 `check-rooms` 机器检查。

## 五、可选针脚

```js
const provider = {
  capabilities: () => ['issues', 'comments', 'ack'],
  list: async (context) => {},       // 必需
  cursorOf: (item) => {},            // 必需
  compareCursor: (a, b) => {},       // 必需
  listComments: async (context) => {}, // 可选
  acknowledge: async (context) => {},  // 可选
}
```

普通 issue 监控只插 `list/cursorOf/compareCursor`；onlyNewComments 需要 `comments`；watch_ack 需要 `ack`。缺少被配置要求的能力时，工具明确报错、面板禁用，不能假装已开启。

每个 provider 必须过同一套一致性套件；替换为 fake provider 后，状态与决策房测试仍须全绿。

## 六、迁移

- 老 watcher 保留 v1 行为，新 watcher 默认 v2；迁移由 `state-migration.js` 显式完成。
- v1 `seen` → 该条 legacy 基线；`pending` → 未处置交付；`acked` → 处置记录。
- legacy cursor 与新版指纹不能直接比较：第一次 v2 轮询只对齐当前 cursor，不重放整页；旧 pending 保留重试资格。
- 已交付、已处置记录不得因迁移丢失。迁移必须幂等、不原地修改输入、拒绝未来 schema。

## 七、逐房验收

1. **状态房**：I1–I5、行级 LWW、v1→v2、自 ack、防旧快照；随机事件序列不变式。
2. **决策房**：未列条目持续候选、retry 派生、限额、截断；变异必须红。
3. **数据源房**：必需/可选针脚、能力缺失明示、GitHub/Gitee/fake 一致性。
4. **交付房**：只有成功回执才提交 delivered；失败、忙、删除均不提交。
5. **调度房**：恢复清退避、立即真执行、无双轮、NO_POLL 契约。
6. **投影房**：面板/工具/诊断同一状态同一结论；只读，不回写。
7. **集成**：完整 preflight、依赖边界、双向变异、另起实例装配测试。

## 八、不做

- 不引入数据库或全事件溯源；当前规模一张 JSON 表足够。
- 不靠修改 GitHub Notifications 的用户已读状态。
- 不把「只读接口」包装成大量空实现；可选针脚必须真的可选。
- 不以模块数量增加冒充解耦；房间必须能独立替换和独立验收。
