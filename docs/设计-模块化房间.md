# 主理鱼模块化房间设计（实验仓）

基线：`dsh-session-superagent@1.0.0` / main `95b5a72`。目标是在现有水位 v2 上补齐官方原型中适合单人产品的能力，不引入飞书、多人授权或团队多角色。

- **官方**：Source/Policy/Ticket/Executor/Delivery 全套组织级模型，UI 与宿主功能同插件但按 `src/client`、`src/app`、`src/core`、`src/executor` 分层。
- **我们**：保留主理鱼现有 watcher 与水位 v2，只新增单人需要的独立小房间和显式宿主端口；飞书、多人和团队角色不进入依赖图。
- **为什么更好**：保留已验证的 GitHub/Gitee、UI 和交付能力，只补真实缺口；每个房间可独立测试、独立合并，不把单用户产品变成团队编排系统。

## 总体约束

- 每房只写自己的实现与测试；生产入口、路由、面板总装和依赖检查由 Lead 统一修改。
- 纯函数房间不得读 `process.env`、不得直接联网或写宿主状态；I/O 通过显式端口注入。
- 所有状态转换返回新对象，不修改入参；投影只读并冻结。
- 未完成、未知和明确空集合必须区分；未知计数用 `null`。
- 不复制水位 v2 的 `obs`：Ticket 管执行生命周期，`obs` 继续管外部条目交付/处置。

## 共享 DTO

### Ticket

```jsonc
{
  "id": "ticket:github:o/r#1",
  "threadKey": "github:o/r#1",
  "status": "open | assigned | waiting | ended",
  "ownerSessionId": null,
  "workdir": null,
  "assignmentId": null,
  "resumeCount": 0,
  "createdAt": "ISO",
  "updatedAt": "ISO",
  "endedAt": null,
  "endReason": null,
  "history": [{ "at": "ISO", "type": "created|assigned|waiting|ended|resumed", "detail": "" }]
}
```

只有显式人类动作可以 resume；后续评论归属与执行生命周期是两个不同决策。

### ThreadSubscription

```jsonc
{ "threadKey": "github:o/r#1", "ticketId": "ticket:github:o/r#1", "sessionId": "session-a", "active": true, "createdAt": "ISO" }
```

`routeThreadEvent` 只返回 `deliver / resume / eval / ignore` 及归属，不直接唤醒或执行。订阅记录另存 `ticketStatus/endReason`，总装通过 `syncTicketState` 同步；ended 后的人类普通评论可 resume，`human-stop` 不得自动复活。

### Assignment

```jsonc
{ "id": "assign:<ticket>:1", "ticketId": "ticket:github:o/r#1", "sessionId": "worker-session", "workdir": "absolute path", "status": "assigned|waiting|ended", "attempts": 1 }
```

Executor 端口由宿主注入：`start / prompt / status / stop`。房间不自行创建子代理。

### OutboxMessage

```jsonc
{ "id": "deterministic-id", "ticketId": "ticket:github:o/r#1", "channel": {}, "body": "", "status": "pending|sending|sent|failed|gone", "attempts": 0, "nextAt": "ISO", "createdAt": "ISO", "updatedAt": "ISO" }
```

持久化由 `commit(nextState, expectedState)` 端口完成；生产接线使用现有单写者状态事务。重复消息 ID 不得产生第二次外部发送。claim 写入带宿主编号的 `leaseUntil` 租约，只有租约过期才允许其他进程 recover；活跃租约不能被当成崩溃残留重发。GitHub/Gitee 评论带不可见 marker，worker prompt 复用稳定 messageId。

### Admission

确定性 gate 先执行，只有 gate 放行才调用 assessment。模型 assessment 不能推翻确定性拒绝；结果必须带 stage、disposition 与 reason。

## 验收

1. 每房独立测试覆盖正常、反向、幂等、重启/并发边界（适用时）。
2. `scripts/check-rooms.mjs` 扩展到上述房间，禁止跨房拿内部实现。
3. Lead 集成后才修改 `lib/index.js`、`client.js`、package exports、路由与文档。
4. 全量测试、隔离 profile、另起实例、独立审查全部通过前不推送；验证后只推独立实验仓。
5. **UI 模组另设人工门禁**：先本地展示官方对照截图与真实交互，用户明确确认前，即使自动测试通过也不推送。
6. **双盲 Debug**：每批产物至少两组互不知情的独立审查，A 核心黑盒对抗、B 官方 UI 对照；不得预先提供实现思路、已知问题或其他审查结论。
